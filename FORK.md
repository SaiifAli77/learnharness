## Rules for fork changes

- Keep edits to upstream files minimal: new files plus one-line hooks. Never edit upstream tests; skip them in `scripts/fork-test.mjs` instead.
- Every feature has a fork test.
- One commit per feature. Amend or fixup into the feature's commit rather than stacking new commits on top, so the stack stays short and rebases stay cheap.
- Fork docs live in this file only. Upstream's `README.md` and `docs/architecture.md` stay unmodified.
- The project skill `/learnharness` (`.claude/skills/learnharness/SKILL.md`) holds the full procedure.

### Architecture, section 8.2

Formerly added to upstream's `docs/architecture.md`, after section 8.1:

#### 8.2 Local agent connections (Claude Code, Antigravity)

A second subscription class where LearnHarness owns **no credential at all**: the learner installs and signs into a vendor runtime themselves, and the app drives it over that runtime's documented local protocol. Routes `claude-code` (the learner's own Claude Code CLI, spoken to directly over `claude -p --input-format/--output-format stream-json` — no Anthropic SDK is bundled) and `antigravity` (Google's official Antigravity ACP server, spoken to over the Agent Client Protocol via `@agentclientprotocol/sdk`) are distinct persisted routes that never fall back to API keys. The app never runs a claude.ai or Google OAuth flow of its own and never reads a token: Claude Code keeps the `claude auth login` sign-in; Antigravity's sign-in is requested *inside* the ACP server (`authenticate`, Google method), which opens the browser and stores the tokens itself. Status reads only what the runtimes report (`claude auth status --json`; Antigravity token *presence*). Everything runs in the server child (Electron main hosts no inference — §8), so the web build works too. The only persisted state is `data/local-agents.json`: per connection `{enabled, allowBackgroundUse}` (default off / on), written by `src/store/local-agents.ts` (through upstream's `writeFileAtomicSync`) and injected into the agent layer by `src/server/local-agents.ts`.

**Park within a run** (`src/agent/local-agents/run.ts`). The runtimes run their own agent loop; pi-agent-core runs the app's. One `LocalRun` is one live CLI conversation spanning several pi model steps: a cold start spawns the runtime with the prior conversation rendered as tagged transcript blocks (`transcript.ts`, deterministic and append-only so prefixes cache); the app's current tools are exposed through a loopback MCP server (`mcp-server.ts` — 127.0.0.1, per-run bearer token, capped bodies, hand-rolled Streamable HTTP so parked `tools/call` requests answer over SSE with keep-alives); a tool call surfaces to pi as a `toolCall` and the step ends `toolUse` while the MCP request stays parked; the next `streamFn` call resumes the SAME process only when it carries exactly the pending call ids' results, nothing else appended, and the same prompt/tools/model/level signature — anything else closes the run and cold-starts. A question tool's dangling call therefore parks across the learner's answer (20 min idle cap; at most 6 live runs, LRU-evicted); a turn that ends without a tool call releases its process. Claude declares calls in its stream (`tool_use` blocks) before the MCP request arrives; ACP surfaces them on arrival (150 ms batching).

**Isolation.** Claude Code: `--tools ""` (no built-ins), `--setting-sources ""` (no settings files, hooks or CLAUDE.md — verified with a canary; the child also gets `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`), `--disable-slash-commands` (no skills), `--strict-mcp-config` + `--allowedTools` (only the bridge), `--permission-mode dontAsk`, `--system-prompt-file` (the app's prompt replaces Claude Code's), `--no-session-persistence`, an empty private working directory, and a child environment with every app-held provider key and every auth/base-URL reroute (`ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, Bedrock/Vertex switches, …) removed — so a key saved in LearnHarness can never silently bill instead of the learner's plan. (`--safe-mode` is NOT usable: it also drops `--mcp-config` servers.) Antigravity: no filesystem or terminal client capabilities, the bridge as the only extra MCP server, the `default` (prompting) mode, every `session/request_permission` rejected — the agent's native file/shell tools never run — and the same empty private directory.

**Admission and accounting** ride the shared subscription machinery (§8.1): `isSubscriptionProvider` covers both routes, so the request cycle, background consent (default ON, per connection, withdrawn consent aborts background work), and `nativeSubscriptionError`'s no-fallback copy all apply; the admission scope is the connection generation, which bumps when enabled/account/binary identity changes and closes that provider's runs. Catalogs: Claude is pi-ai's Anthropic catalog without dated snapshots (4.6-generation windows capped at 200K — Claude Code serves `[1m]` separately); Antigravity is discovered from the server's `model`/`thought_level` selectors (pi thinking levels map onto the advertised `thought_level` values). Usage displays as the plan label ("Claude", "Antigravity"), never dollars. Binaries resolve `LH_CLAUDE_BIN` / `AGY_ACP_BIN` → PATH → the login shell's PATH (GUI launches lack it) → vendor install locations.

## Auto-sync

`.github/workflows/fork-sync.yml` runs every 6 hours and on demand. It asks GitHub for upstream's latest published release. If this fork already has a release with that tag, it stops. Otherwise it:

1. fetches the upstream tag (upstream tags are not copied into this fork) and rebases the fork's patches onto it (`git rebase --onto <tag> <old base>`). If `main` already contains the tag, it skips this and just builds,
2. runs upstream's release gates (typecheck, tests via `scripts/fork-test.mjs`, lint, native renderer tests, build, smoke tests),
3. builds the Linux AppImage,
4. force-pushes `main` with `--force-with-lease` pinned to the pre-rebase commit, then publishes a release with the same tag, containing the AppImage and `latest-linux.yml` (the AppImage embeds its block map).

The release notes list the fork patches on top of the tag and include a `git range-diff` of what each patch changed in the rebase. The same list and range-diff go to the run's step summary.

The installed app's updater reads only this fork's releases. Nothing is pushed or released if any step fails. If the rebase conflicts, the workflow aborts it and opens an issue; nothing is pushed.

`.github/workflows/fork-preview.yml` ("Fork conflict preview") runs daily and on demand. It rebases the fork's patches onto upstream's current `main` in a throwaway branch, with no tests, build or push. On a conflict it opens the issue "Fork sync: upcoming conflict with upstream main"; when a later run rebases cleanly (or upstream `main` is already contained) it comments and closes that issue. It gives you early warning before a release lands.

## Claude delivery rule

On Claude models the app makes `send_to_user` the learner's only visible channel (`src/agent/claude-delivery.ts`). The system prompt ends with a one-line "Delivery rule", and an opening section, "How your words reach the learner", also leads it. The upstream prompt body repeatedly says to write prose before a check, and the closing rule alone didn't hold for Sonnet 5.5. Both are fixed text, so the prompt stays deterministic. `tests/claude-delivery.test.ts` pins them.

Since upstream v0.5.0 (#434, "Claude teaching-prose guard"), upstream closes the teacher's prompt with its own `SEND_TO_USER_DELIVERY_RULE` and blocks a teacher question whose thinking is marked as narration when no prose was delivered (`src/agent/narration-guard.ts`). Upstream also no longer gives `send_to_user` to practice, which uses ordinary prose, so the fork's delivery text and guard apply to the prober and teacher only. The fork keeps its preamble on both. Upstream's teacher rule replaces the fork's closing rule on the teacher; the prober, which has no upstream rule, keeps it (`forkDeliveryPrompt`). The fork's `deliveryGuard` also stays, on both agents, running after upstream's guard (`withForkDeliveryGuard`). It bounces a question once when nothing was delivered since the learner spoke and the question's message has a thinking block that may hide prose: one with no signature (what the Claude Code/Antigravity bridge emits, `src/agent/local-agents/run.ts`, where upstream's guard can never fire) and non-empty text, or one upstream's `isNarrationBlock` marks as narration. On OpenAI-compatible APIs (OpenRouter) pi-ai stores the signature as the reasoning field's name (signed, not narration) or as the JSON of `reasoning_details`; that JSON is parsed and counts as narration when any entry's `signature` does. Plain signed thinking on an API connection passes, as upstream intends. A bounce already in the window, the fork's or upstream's (`NARRATION_BLOCK_REASON`), lets the next attempt through, so the fork never bounces after upstream has. The hook in `src/agent/teacher-agent.ts` is one import plus two wrapped upstream lines, gated by upstream's `sendToUserApplies`. `scripts/fork-test.mjs` skips two upstream guard tests whose "plain thinking" is unsigned, which the fork treats as bridge thinking; `tests/claude-delivery.test.ts` covers the bridge, signed-plain and narration-signed cases.

## Typing and streaming stay fast in long chats

`components/chat.tsx` wraps the transcript map in `useMemo`, and `ToolContentResponse` (`components/ai-elements/message.tsx`) is wrapped in `memo`, so a keystroke in the composer or a question dock no longer re-renders every transcript block (367-message chat: ~180 ms -> ~30 ms per keystroke, pixel-identical). `tests/fork-transcript-memo.test.ts` recomputes, with the TypeScript checker, every Chat-scope value the block reads and fails if the deps array is out of date. Two of those values, `pending` and `malformedQuestions`, are rebuilt on every render, so the deps list their inputs (`messages`, `nativeMessages`) instead. The test's `DERIVED` table records that, and a second test fails if upstream starts computing either value from anything else.

While a reply streams, the memo alone doesn't help: each streamed chunk makes the session model re-project the whole view, so `messages` is new and every row used to render again. The memo now calls `forkRows` (`components/fork-transcript-rows.ts`) instead of `messages.map`, with the same row callback. While `busy`, `forkRows` hands back the previous React element of a row when its view message is deep-equal to the one the element was built from, its signature is equal (index, whether it is the last row, the phase at the row and the row before, the anchor of each of its parts), and every other value the callback reads (`busy`, `status`, `compacting`, `hiddenOldest`, `setPlanOpen`, `draftRef`, `send`) is unchanged; a change to any of those drops the cache. The comparison is strict: object keys must also be in the same order, because tool cards show `JSON.stringify` of their input. A row holding a background-job dispatch part (`research`, `pdf`, `demo`, `slides`, `visual`, listed in `FORK_ROW_DISPATCH_PARTS`) is never reused, because its card computes the job's elapsed seconds from `Date.now()` while rendering. When not busy it renders every row as before and drops the cache. `pending` and `malformedQuestions` are read only behind `!busy`, so they aren't tracked. On a synthetic 300-message chat a streamed chunk went from about 70–90 ms to 7–8 ms of projection, render and commit (median of 30 chunks) (linkedom, production React; a browser adds layout and paint for the rows that do change). `tests/fork-transcript-memo.test.ts` fails if the row callback reads a value that is in neither the signature nor the epoch, reads a per-row value in another form, or reads `pending`/`malformedQuestions` where `busy` can be true. It also derives, from the artifact registry, the renderers that can render `DispatchCard` and fails if that set differs from `FORK_ROW_DISPATCH_PARTS`, or if the row renders `DispatchCard` some other way. `tests/fork-transcript-rows.test.ts` loads `components/chat.tsx`'s real row callback, replays a streamed turn (thinking, text and tool deltas, a marker that pushes the streaming row off the end, a late result for an older row, the settle) and checks at every step that the markup with the cache equals a plain `messages.map`, and which rows were reused. A mounted test (react-dom in linkedom) checks that a running job's elapsed time keeps updating in the cached transcript while another row changes, and another that reordered tool input and output reach the tool card.

The two contexts Chat provides, `ChatActionsContext` and `SessionMermaidContext`, used to get a new object on every Chat render, which re-rendered every artifact card, image card and Mermaid diagram on each chunk and keystroke. `components/fork-chat-contexts.ts` returns the same fields with the same behaviour from `useMemo`, rebuilt only when `chatId`, `syncFromServer`, `send` or a state setter changes. The hook in `chat.tsx` is the two `value={…}` expressions plus one import. `tests/fork-chat-contexts.test.tsx` checks the values stay the same object across re-renders, change with each input, behave as before, and cover every field of both context types.

## Opening long chats fast

A long chat used to SSR and hydrate every transcript block before showing anything. Now the transcript first renders only the newest 6 messages (server and first client render agree, so hydration matches), then, after mount, ONE idle-scheduled transition renders all the older ones at once (batches re-rendered the visible transcript each time and took ~10 s). A scroll hold in the same hook tracks the reader's distance from the bottom and restores it when older messages are prepended: at the bottom stays at the bottom, scrolled-up text does not move. The settled page is pixel-identical to before. Measured on a 44-block chat: usable at the bottom in ~4.2 s (was ~13 s), typing during the fill ~16 ms median.

`components/transcript-fill.ts` holds the hook; `components/chat.tsx` renders hidden messages as `null` and keeps the absolute index `mi`. The full transcript is forced at once by a URL hash at mount, `hashchange`/`popstate`, and the in-chat Find opening. Graph links to an old message (`propositionSessionHref` in `src/core/session-navigation.ts`) carry `?full=1`: `app/chat/[id]/page.tsx` reads it and passes `initialFullTranscript` to `Chat`, so SSR and the first client render contain the whole transcript, as before the fork change. Two upstream tests that assert the exact href are on the skip list in `scripts/fork-test.mjs`. `tests/fork-transcript-fill.test.ts` guards it, and `hiddenOldest` is in `forkRows`' epoch, so revealing older messages during a turn renders every row again.

Remaining trade-off: using in-chat Find within the first seconds waits for the older messages to render.

## StatQuest method and slide decks

The teacher teaches any step with numbers in it the StatQuest way (problem first on a tiny dataset, freeze all but one, real numbers every step, the term after the concept) and shows the subject as narrated slide videos. The doctrine is `src/agent/prompts/teacher/36-statquest.md`, picked up by filename. The flow: once the learner confirms the plan, the teacher asks with `ask_user_question` how many minutes of narration the subject video should have (10, 15, 20 or 25, one marked recommended by difficulty, each shown with its expected play time since the pauses make it play about 1.4× longer, or the learner's own number). Every part must have 80–120% of its share of the narration (the pick ÷ the number of parts × 135 words, so 15 minutes in 3 parts is 540–810 words per part), the pick is capped at 25 minutes, and a part is at most 7 minutes. The teacher then sends ONE subject video, the whole subject end to end as one continuous story (not organised by plan nodes), as several `slides` calls with `kind: "subject"`, each a consecutive part of about 5–7 minutes with its own stage and the same colours and numbers. While it builds, the teacher lets the learner try to invent the subject from the start: it poses the problem and asks, one `ask_user_question` at a time (no `quiz`/`explain`, so the plan map and the node-video gate are untouched), how they would attack it, reacting without giving the answer away. When the video arrives the questions stop, the learner watches it and sends a message, and node 1 begins. Node videos (`kind: "video"`, 3–6 minutes, about 550 words, with a `nodeId`) are built two nodes ahead: nodes 1 and 2 while the subject video builds (the completing subject part's ACK names them, when headless rendering is available, skipping any already running or done; the line is saved on the job as `nodeVideosAck`, so a replayed call gets the same ACK), and at node k the videos for the next two nodes. At a node whose video has arrived, the teacher points the learner to it first, waits for them to watch it, then teaches the node in full (worked numbers, predict and check questions, the closing essay); the video never replaces the teaching. Short decks (`kind: "deck"`) come only when the learner asks for one.

`slides` is a teacher-only job tool (`src/agent/fork-slides/tools.ts`, spread into upstream's `jobTools()`; the prober only takes `research`/`pdf` from it, so it never sees `slides`). The teacher sends a script: a title, `kind` (`subject`, `recap`, `video` or `deck`), an optional `continues` (the toolCallId of an earlier finished deck or node video in the session), the stage (the fixed diagram, with one colour per quantity) and slides of build steps (`say`, `show`, optional `pointer`, and `numbers`, each a displayed `value` plus the `expr` it comes from). A video also carries `nodeId`; a subject part carries `part`, `of` (at most 8) and `minutes`. Dispatch checks the call before any job exists and returns every problem to the teacher. It rejects a number whose expression doesn't parse or doesn't round to its displayed decimals (`src/agent/fork-slides/expr.ts`, a small parser with no `eval`), more than 45 slides, 6 steps per slide or 120 steps (per part for a subject video), a video outside 400–850 spoken words (the message gives the count, how many words to add or cut, and the 550-word aim) or whose `nodeId` is not on the chat's plan map, a subject part whose `minutes` (whole minutes) is over 25 (the message says to use 25 and tell the learner), whose minutes ÷ `of` is over 7 (the message says how many parts are needed), or whose own words are outside 80–120% of `minutes ÷ of × 135`, and a `continues` that is not an earlier slides deck in the chat. A deck that is still being built or failed counts as no deck; the subject video and subject parts can't be continued. The ACK tells the teacher what to do: a deck IS the explanation and takes a few minutes, so write the setup, then keep the learner working meanwhile without explaining what the deck will show. For a node video, carry on with the current activity while it builds (the invention questions during the subject video, otherwise prose teaching); at its node, point the learner to it first, wait for them to watch it, then teach the node in full. For the subject video, keep the learner busy with warm-ups, then tell them to watch it and send a message when done.

Subject parts are collected per chat on disk (`<data root>/fork-slides/subject-parts/<chatId>.json`, the chat id checked against a strict pattern). A part that does not complete the video gets the ACK "Part i of n received; send the rest (still missing: …)" and no job; its tool part renders a quiet "part i of n received" line (`ForkSlidesDispatchCard`, the `slides` renderer) instead of a dispatch card that would wait forever. Sending a part number again replaces that part. Every part carries the same `of` and `minutes`; part 1 sent with a different `of` or `minutes` starts the video over, and any other part that disagrees is rejected. When parts 1 to `of` are all in, the call that completed them creates ONE job holding every part in order (title: part 1's) and each part's call id, and the collection is cleared. The collection is written with upstream's `writeFileAtomicSync`. The `slides` tool runs sequentially (`executionMode: "sequential"`), and the collection check (the same `of`/`minutes`) runs again inside the synchronous read→check→write step, so parts sent in one message are checked against each other. A replayed part call that is already in a saved subject video gets the ACK it originally got (the completing call: the dispatch ACK; an earlier part: "Part i of n received.", which the card still recognises) and leaves the collection untouched. A collection whose every call already sits in one saved subject job (a crash between creating the job and clearing the collection) is discarded before the next subject part is handled; one with any call not consumed is kept.

**The node-video gate** (`src/agent/fork-slides/node-video-gate.ts`). `createTeacherTools` passes its quizzing tools through `forkNodeVideoGate`, which wraps `quiz`/`explain`. A question that is otherwise valid, on a node k not yet reached, is rejected once (an error tool result, so the teacher acts in the same turn) unless `slides` is switched off, headless rendering is unavailable (`getHeadless().unavailableReason()`), a subject video job is running, or nothing is missing. The targets are exact: `nextVideoTargets` takes the plan nodes in order, not reached and not k, picking first a node whose prerequisites (plan edges) are all reached, k or already picked, else the first one left, up to `NODE_VIDEO_LOOKAHEAD` (2). A target is covered by a node video job for it that is running or done, and excused when its newest node video job failed (only that node, so a failing video can't trap the teacher). The message names each missing node by id and title, says they are the nodes after k, not k, and carries the marker `NODE_VIDEO_GATE_MARKER` ("Node videos are built ahead", in `src/core/fork-slides.ts`; the text goes on "(two nodes ahead of the learner)"). "Reached" is upstream's plan-position fold (`derivePlanStatusesLh`) over the persisted record plus the nodes rejected in this process: a rejected call is persisted with its nodeId at the end of the turn, so later turns (and restarts) let the node through, and within the rejecting turn the in-memory rejection does, and the second attempt always passes. While a rejection is pending, the `slides` tool rejects a video for k or a node already passed with only that message (no word-count or other problems), naming the targets instead. It is pending only within the rejecting turn (the persisted record still has the message count it had at the rejection; calls persist at turn end, so the next turn, after an abort or error too, sees a longer record) and until any quiz/explain call passes the gate (the re-posed question on k, or a question elsewhere when the teacher moves on); a new rejection replaces it. Outside a pending gate a video for any node is allowed. The same `nextVideoTargets` names nodes 1 and 2 in the subject video's ACK.

**Hidden retries.** Upstream shows every errored tool call as a quiet "Retrying…" line. `components/fork-hidden-tool-error.ts` (`forkHiddenToolError`) hides it for a rejected `slides` call and for a quiz/explain error carrying the gate's marker; aborts and every other error render as upstream renders them. Each hidden retry is its own model step, so `forkHiddenStep` also drops the separator of a step that holds only hidden errors (no column of blank hairlines). Display only: the error stays in the record and the model's context. The hook in `components/chat.tsx` is one import and one line just above upstream's "Retrying…" branch plus one line in its `step-start` case; `tests/fork-hidden-tool-error.test.ts` guards it.

The job is an upstream `demo` job whose saved input carries a `forkSlides` marker, so there is no new job kind (the activity dock says "demo", and the arrival text says "The demo … is built"; the result `notes` tell the teacher it is a narrated deck and what to do next; for a node video: at its node, point the learner to it first, wait for them to watch it, then teach the node in full, without retelling it). It runs on the teacher's engine (Strong slot), not the demo builder's: `src/agent/fork-slides/runner-hook.ts` picks the engine and the refusal tier, and runs the slide helper `src/agent/subagents/fork-slides-maker.ts`. A subject job runs one helper per part in parallel, each on its own stage. A part that fails is retried once (never after an abort). If it still fails, the video is delivered without it: the card shows "Part 3 of 5 could not be drawn.", and the notes name the part and tell the teacher to cover that stretch in prose. If every part fails, the job fails as before. The helper never sees the lesson. It writes one stage SVG whose top-level parts carry ids (with a `box-<id>` rect for anything that gets red-boxed), and for each build step declares a state relative to the stage: which parts are lit, which are hidden, which boxes are shown, and overlay items that persist within the slide until removed. Code assembles every frame from stage plus state (`src/agent/fork-slides/frames.ts`: unlit parts at 0.2 opacity, shown boxes forced red), so the stage cannot drift. Every frame is rendered and shown to the model at full size, at most 6 per message. After a fix only changed frames are shown again, and the helper cannot finish until the current version of every frame has been seen. At the iteration cap (100 model calls) it fails honestly instead of delivering unseen frames.

Frames are stored on disk at `<data root>/fork-slides/<jobId>/` (derived from `SETTINGS_FILE`), and the result holds only references plus the script text, which keeps chat files small. Each slides job starts with a lazy sweep (`sweepForkSlidesOrphans`, no upstream hook): it removes job folders (job-id names only) whose job file (`<PATHS.data>/jobs/<id>.json`, where the job store keeps it) is gone, and subject-part collections, including atomic-write temp files `<chatId>.json.tmp-…`, whose chat file under upstream's `PATHS.chats` is gone, so deleted chats leave no slides behind. Existence is read from the files, never from a parse that can fail transiently. A subject video's files carry a part prefix (`p2-stage.svg`, `p2-frame-03-1.svg`, `p2-audio-03-1.ogg`, parts 1–8), so a 25-minute video never outgrows the two-digit slide numbers; the unprefixed names of older decks stay valid. The delivered subject video is ONE deck: its slides from every drawn part in order, each slide carrying its `part`, plus `parts: { of, missing, calls }`, so the card plays straight through as one timeline and shows "part p of n" by the step counter. Old results (no part fields) render as before. `app/api/fork-slides/[...path]/route.ts` serves them read-only with strict id and file-name checks, plus a generated self-contained `deck.html` (frames as image documents, transcript, a stepper) for download. `components/artifacts/fork-slides-card.tsx` is the arrival card: the frame, the slide's transcript with the current step emphasised, ◀ n / N ▶ by slide, Space or a click for the next build step, arrow keys while focused, the figure card's invert and download buttons, and an expand button (see Narration). `slides` can be switched off in Settings like the other job tools.

The knowledge-graph extractor and the session Markdown export read each deck's title and spoken narration as teacher prose (`forkSlidesNarration`, hooked into `userFacingTextOf` in `src/core/native-messages.ts`), because the teacher doesn't repeat a deck in prose. Only narration the learner actually got counts (`forkSlidesDelivered` reads the transcript's `subagent-steer` messages that carry a drawn slides result): a deck or node video once its result is delivered; a subject part only when the delivered video's `parts.calls` lists its call and the part is not in `parts.missing` (the subject job input keeps each part's call id). Every other slides call is skipped (`forkSlidesFailedCalls`, hooked into `failedOutputCallIds`): still building, failed, aborted, rejected, a replaced part, a part of a restarted or never-completed collection, and any call in an aborted or errored assistant message. Coverage fingerprints are computed over the whole transcript, so a message re-opens for extraction when its video arrives. Every real caller passes the whole-transcript set (coverage, the extractor's batches, `transcriptView`, `sessionMarkdown` for the export route). Only the single-message defaults of `messageViewLines`, `messageFingerprint` and `messageMarkdown`, which no real path uses, would leave delivered narration out.

**The model's view of delivered calls** (`src/agent/fork-slides/slim-history.ts`, one hook line in `src/agent/teacher-agent.ts`: `convertToLlm: (messages) => toLlmMessages(forkSlimDeliveredSlides(messages))`). Once a slides call is delivered (for a subject video, every part call, a missing part included), the model sees its arguments as `title`, `kind`, `nodeId`/`part`/`of`/`minutes` where present, `stage` (so a later `continues` deck can name the same parts and colours), `narration` (the `say` text per slide) and a `trimmed` note. Calls still building, rejected, failed, aborted or never delivered keep the full script. The latest assistant message and every other block (thinking and signatures included) pass through unchanged, and the persisted record is untouched. The delivered set is computed once per conversion (linear). A realistic 12-slide, 48-step node video script goes from 14,641 to 5,139 characters (65% smaller, the stage kept) in every later request. All agent engines, including the Claude Code and Antigravity bridges, receive history through pi's `convertToLlm`; the local-agent resume keys hash only text and call ids, so slimming never forces a cold start. Two paths read the record directly and still see the full script: compaction's summary input (`serializeForSummary`) and its token-estimate fallback.

**Narration** (`feat(fork): Kokoro narration, the subject video and node videos`). After the frames are verified, each build step's `say` is synthesised into its own Ogg Vorbis file next to the frames (`audio-SS-T.ogg`; a subject part's `pN-audio-SS-T.ogg`, every part in one Kokoro session), and the result stores each step's file name and duration. `src/agent/fork-slides/tts.ts` resolves the learner's own `uv` like the local-agent binaries (`LH_UV_BIN`, PATH, the login shell's PATH, known dirs) and runs `uv run --quiet --with kokoro-onnx==0.6.1 --with soundfile==0.14.0 python -I <script>` (both pinned). The Python script is a string constant written to a temp file at runtime. One process per job loads the model once and answers JSON lines. The model is Kokoro v1.0 int8 (`kokoro-v1.0.int8.onnx`, about 88 MB) with `voices-v1.0.bin`, both downloaded once into `~/.cache/kokoro` from the kokoro-onnx release assets (`https://github.com/thewh1teagle/kokoro-onnx/releases/download/model-files-v1.0/`) when missing. The voice is `am_michael` at speed 0.85 (it was 0.95; decks built before keep their audio), `en-us`. App-held keys are stripped from the child's environment. A failed step (an error reply, a timeout or the process dying) is retried once, and a dead or stuck process is restarted once per deck from the same temp script, continuing from that step; an abort is never retried. If uv, the download or the synthesis still fails, the deck is delivered without audio and the notes tell the teacher which step failed and that it was retried. The route serves `audio/ogg` with byte ranges. The card's player has play/pause, a scrub bar across the whole deck and elapsed/total time. Playback runs through every build step in order with the frame in sync, with 1.2 s of silence after each step, 2 s instead when the next step is on a new slide, and none after the last step. The pauses are part of the pure timeline (`deckTimeline`: `STEP_PAUSE`, `SLIDE_PAUSE`), so the total, the scrub bar, seeking and the clock count them. A time inside a pause belongs to the step that just ended (its frame stays; playing resumes the rest of the silence, then the next step). The pauses are player-side, so older decks get them too. The delivered notes give the length with the pauses; ◀/▶ still move by slide (the audio jumps to that slide's start), Space toggles play, and the transcript highlights the step being spoken. The expand button makes this same live card fill the app window with CSS (`fixed inset-0 z-50`, the z-index upstream's full-window dialogs use). The frame is scaled to the window height with the transcript and controls below it, and the player, keys and invert keep working with nothing remounted. Esc exits from anywhere, and focus returns to the button. The browser Fullscreen API is not used, because the desktop app's permission handler (`electron/main.cjs`) denies `fullscreen`, so `requestFullscreen()` never settles there. A write to Kokoro's stdin after its reader closed (EPIPE) is handled as a dead session, which the retry and restart rules cover, instead of crashing the server. The timeline functions in `src/core/fork-slides.ts` are pure. A video is simply a `kind: "video"` deck. On this machine the int8 model speaks about 1.5× faster than real time after a ~1.5 s model load. `tests/fork-slides-narration.test.ts` guards it (fake spawner, no real uv). The pause clock (every 100 ms) and the audio's `timeupdate` re-render the card, so the frame is drawn through `FrameImage`, a `memo` of upstream's `SvgImage`, which otherwise repairs and URI-encodes the whole SVG on every render (about 2.5–5 ms for a 250 KB frame); `tests/fork-slides-frame.test.tsx` guards it. The downloadable `deck.html` carries frames and transcript only, no audio. Narration audio is a build-time artifact; the knowledge graph reads the narration text through the hooks above, not the audio.

**The recap video** (`feat(fork): recap video`). After the learner passes the last plan node's closing essay, the teacher asks once with `ask_user_question` whether they want a recap video of what they learned, with the subject video's length options (10, 15, 20 or 25 minutes of narration with the expected play times, one marked recommended, or the learner's own number) and a "No thanks" option; a declined offer is not repeated. The learner may also ask for one at any time; before every node is finished it covers the nodes finished so far and its first narration line says so (prompt only, no app check). The recap retells this session end to end as one story in plan-node order, with the session's own toy examples, datasets, numbers and colours, and spends extra time on what the learner got wrong or struggled with (gaps in closing essays, missed checks, repaired misconceptions), showing the wrong idea, why it fails and the corrected one on the picture. No new material. It is `kind: "recap"` on `slides` and reuses the subject video's parts machinery exactly, through the same code: `part`/`of`/`minutes` on every call with the same caps, the same 7-minute part limit and per-part word range (`partLengthProblems`, its messages naming the recap where the subject's name the subject video), the same replace/restart/mismatch rules, the sequential collect step, replayed-part ACKs, the crash discard, one job when every part is in, parts drawn in parallel with one retry and the card note for a part left out, and "part p of n" by the step counter. Its collection is its own (`<data root>/fork-slides/recap-parts/<chatId>.json`, the same chat-id check, covered by the orphan sweep), so a subject collection and a recap collection in the same chat never interfere, and after a recap is built a new part 1 starts another one. A recap part never takes `continues`, and nothing can continue a recap. The completing call's ACK tells the teacher to say the recap video is being built and will arrive as a new message, then wait: no questions or teaching, no `quiz`, `explain` or `ask_user_question` meanwhile; when it arrives, tell the learner to watch it. The runner's notes say it is the narrated recap video, n of `of` parts, name a part left out and say to cover that stretch in prose, as for the subject video. The card's kind label reads "recap video", and the quiet "part i of n received" line and the downloadable `deck.html` work as for the subject video. Once delivered, recap part calls are slimmed in the teacher's view like subject parts. Recap narration is in neither the knowledge graph nor the Markdown export: `forkSlidesNarration` returns nothing for a recap call (delivered or not), and `forkSlidesDelivered` never puts a recap call in `narrated`, so a delivered recap never changes a message's coverage fingerprint or re-opens it. The node-video gate only counts `video` jobs and a running `subject` job, so a recap job (running, done or failed) never stands it down or counts as a node video. The helper is told "Kind: recap video, part p of n". `tests/fork-slides-recap.test.ts` guards it.

## Chat list summaries are cached

`listChats` (`src/store/chats.ts`) used to parse every chat file in full and run the phase, pending-question and active-problem folds over every message on each call: the sidebar list, the activity feed, the graph, job recovery and source organisation all call it. `src/store/fork-chat-summaries.ts` keeps each file's summary and reuses it while the file's identity (device, inode, size, mtime and ctime in nanoseconds) is unchanged. A file changed in the last 3 seconds is always read again, since a coarse filesystem clock could give the next write the same timestamps. Failures (unreadable, newer schema version, projection error) are never cached, so their logs and absent rows repeat as before. Every call returns fresh copies, in the same order. Files no longer listed are dropped from the cache. The hook is two wrappers in `listChats`' chain plus one import. With synthetic 1.5 MB chats, a listing took about 45 ms for 4 chats and 470–510 ms for 40 on every call; now the first listing costs the same and later ones about 0.2 ms and 1 ms. `tests/fork-chat-summaries.test.ts` compares every listing with an uncached one across created, rewritten (atomic and in place, same size), renamed-over, deleted, corrupt, newer-version and unprojectable files, and checks that unchanged files are not read again. It also fails if upstream puts any stage between the `forkCachedChat` read, the null filter and the `forkCachedSummary` projection.

## When a "Fork sync" issue appears

The workflow opened an issue: a rebase conflict, a version mismatch, failed checks, or a failed publish. Nothing was pushed. This clone has `origin` = upstream and `fork` = this fork. To resolve a rebase conflict:

```
git fetch origin --tags
git fetch fork && git switch main && git reset --hard fork/main   # main is force-pushed, so reset instead of pull
git merge-tree --write-tree --name-only main <tag>                # preview the conflicts
base=$(git merge-base main <tag>)
git rebase --onto <tag> "$base"                                   # rerere replays previously recorded fixes
git range-diff "$base..ORIG_HEAD" "<tag>..HEAD"                   # check each patch still says the same
npm ci && npm run typecheck && node scripts/fork-test.mjs && npm run lint
git push --force-with-lease fork main
```

If the rebase stops on a conflict, fix the files, `git add` them, and `git rebase --continue`. Then re-run: Actions -> Fork sync -> Run workflow. The workflow sees `main` already contains the tag and just builds and releases.

Enable rerere locally once: `git config rerere.enabled true` and `git config rerere.autoupdate true`. For an "upcoming conflict" issue, resolve it early: rebase a scratch branch onto `origin/main` (`git switch -c scratch main && git rebase --onto origin/main $(git merge-base main origin/main)`), fix the conflict, and finish the rebase. Git records the resolution, so the rebase at release time replays it instead of conflicting again. Delete the scratch branch afterwards.

## One-time setup

- Add repository secret `FORK_PUSH_TOKEN`: a fine-grained PAT for this repo with Contents and Workflows write (the rebase can carry upstream workflow changes, which the default token cannot push).
- Enable Actions on the fork first: Actions tab -> "I understand my workflows, go ahead and enable them".
- Disable upstream's release workflows in the fork: in the Actions tab select each of "Desktop release" (`release.yml`) and "Notify website of public desktop release" (`notify-website.yml`), then "..." -> "Disable workflow". Or run `gh workflow disable release.yml --repo saiifali77/learnharness` and `gh workflow disable notify-website.yml --repo saiifali77/learnharness`. Leave "Fork sync" and "Fork conflict preview" enabled.

## Known limit

The fork's release version equals upstream's version. A fork-only fix therefore ships with the next upstream release, or by installing a build manually.
